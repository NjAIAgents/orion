Concurrency how many agents exist at once
max_concurrent_tickets
How many tickets a watcher works at the same time. It does not bound one agent's behaviour; it bounds how many agents exist.
orion.json3
Above 10 the CLI stops and asks, listing five hazards — conflicts grow with the square of this number (six pairs at four, forty-five at ten), every run holds a worktree off one shared clone that git serialises on, one rate limit is shared by all of them, a budget checkpoint is only read between runs so runs already in flight sail past it together, and approvals do not parallelise: N tickets finishing means N approvals waiting on one person. This panel refuses values above 10 outright — a browser button that auto-answers that prompt would delete the only guard the code has.
max_concurrent_children
Caps how many subagents a fan runs at once. Low by default: unbounded fan-out against a rate-limited API converts a queue into a stampede. This is the hard ceiling — raising a stage's own agent count cannot widen the real fan past it.

qa.max_rounds
QA never blocks on its own authority, so this loop is the only way the stage can stop a run — and it would do it by spending. Each round is a full findings-fix-reverify exchange, and the cost lands on the implementer, the actor that dominates per-ticket spend.
shipped3
ci.max_fix_attempts
Outer bound only — an identical repeated failure already ends the loop at once. Each attempt is an agent run plus a full CI run, and the count survives a restart.
shipped3
discovery.max_rounds
A round buys more questions, not another attempt at one answer — and each round is the whole fan, not one agent. The most expensive round in the system to raise. Past the ceiling Orion escalates what is still open to a person, so a higher number buys elaboration, never a decision.
shipped2
dba.max_rounds
Runs on opus, and only on tickets that touch data — a schema decision is inherited by everything written against it afterwards.
shipped3
qa.verdict_minutes
The one field where LOW is the dangerous direction. This is the floor for the verdict re-ask, not the ceiling — the real budget scales with the run it resumes. A re-ask killed by the clock produces neither a verdict nor a fix round: just an unverified branch and a person sent to read it.

qa.author_agents
Bounds agents, which contend for one rate limit — not processes. Capped in practice by max_concurrent_children above.
shipped5
qa.exec_procs
Bounds processes on this machine, not agents. Too high contends for CPU, disk, and any port the tests bind.

Terminal only shown here, changed there
These are readable in the panel and not editable from a browser. Each one either widens what a run may do, removes a human step, or spends without being asked — and each is one keystroke from a very bad afternoon. The exact command is given; run it in a terminal where the confirmation prompt is real.
budget.weekly_usdterminal only 200
The budget window across every project. Here zero means UNLIMITED — the exact opposite of zero everywhere else in this tab. A panel that treats a cleared field as zero removes the ceiling while looking like it did nothing.
to change it
$ edit budget.weekly_usd in orion.json
vcs.allow_release_branch_mergesterminal only false
Turning this on means Orion merges agent work directly into the release branch and there is no human promotion step left. It is a named key rather than a side effect of editing a string, because giving up that step should take a sentence that says so.
to change it
$ edit vcs.allow_release_branch_merges in orion.json
