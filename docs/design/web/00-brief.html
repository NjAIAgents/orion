Orion web — design brief

Mockups for Jira fixVersion v0.10.0 — epic OR-35 plus the write-capable surface (OR-266, OR-272, OR-279, OR-281). Read this first: it says what I took from the codebase, what I assumed, and what I need you to settle.

Where the visual language comes from

Orion already has a design system — it lives in internal/ui and it is a terminal. I lifted it rather than inventing one, so the browser and the console never disagree about what a run looks like. The rules below are the CLI's own, quoted from its source.

Five verbs, not twenty

The status column answers one question: “do I have to do something”. It has exactly five values — ok, working, waiting, warning, failed. Every card and log row uses these words and no others.

Colour is never the sole carrier

From ui/color.go: every line begins with a word saying the same thing as its colour, so output reads identically piped, logged, or by someone who cannot distinguish the colours. The mockups keep the word beside every dot.

Three colour axes, three columns

Ticket key coloured by ticket, status by outcome, actor by actor. The message is never coloured — its text belongs to the agent that said it.

Name and job title, every line

internal/actors: the name alone is opaque to anyone who has not memorised the cast. So it is “Ravi · backend developer”, always, never just “Ravi”.

The status palette, as the CLI defines it

What the terminal prints today

This is the line the web surface has to reproduce — same columns, same order, same words:

13:34:52 OR-183 ✓ ok Ravi · backend developer opus 2 commit(s) on orion/or-183 13:34:52 OR-183 ══ stage ══ implementing → qa Ravi · backend developer hands to Anita · QA engineer 13:34:53 OR-183 ◐ working Anita · QA engineer sonnet verifying acceptance criteria 13:35:01 OR-266 ⏳ waiting ci - pull request opened, awaiting CI; no agent is running

Note the stage boundary: it drops the icon/verb/actor columns entirely and puts one sentence where they were. Nothing else looks like that, which is what makes a handoff findable by eye. The mockups keep that rule.

Assumptions I made

Dark first

This sits beside a terminal on the same screen. A white dashboard next to a dark console is the jarring part. Light theme is a later variant, not the default.

Monospace throughout

The columns only line up in a mono face, and column alignment is what ui/color.go calls the thing that makes a long report scannable at all.

No invented metrics

Every number shown traces to something Orion records: step counts, elapsed, cost from the budget ledger, CI verdict. No engagement-style charts.

Sample data is real-shaped

Ticket keys, actor names and models come from the shipped roster in internal/actors. Names are configurable, so treat them as examples.

What I need you to settle

1 — The read-only premise is dead. How far?

OR-35 still says “Read-only, at least to begin with” and “Localhost only, no auth”. OR-266 and OR-281 overturn both, and OR-286 exists purely to rewrite the tickets that still cite the old premise. I have designed the board with gate controls. Say if you want the mockup to show the read-only version instead.

2 — Static mockups, or a clickable prototype?

Static screens are faster to iterate on and are what a ticket usually needs. A clickable prototype earns its cost if you want to feel the log-panel filtering and the gate-response flow before OR-51 and OR-281 are built.

3 — Is the gate board the front door, or is the run view?

OR-35 opens on live agent activity. OR-272 says the thing you actually need is “everything waiting on me, across projects”. Those are different landing pages. I assumed gate board first, run view one click away — because the epic itself says the common case is opening it to see what happened.

What comes next

Once you answer those, I build the screens: the run view (OR-51), the gate board (OR-272), a ticket detail (OR-53), and agent config (OR-54). Each one annotated with the ticket it satisfies.
